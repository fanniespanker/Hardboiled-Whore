
# CNML Specification v0.4.1 (Draft)

## Foundations

CNML (Contextual Narrative Markup Language) is a constrained XML vocabulary with semantic rules.

All CNML documents MUST be well‑formed XML.

CNML is primarily an experiential and discourse-oriented representation system.

---

## Core Evaluation Model

CNML evaluation operates across four primary expressive planes:

```text
Narrative × Temporal × Prosodic × Spatial
```

These planes are orthogonal and compositional.

## Planes

| Plane     | Meaning                          |
|-----------|----------------------------------|
| Narrative | discourse, cognition, experience |
| Temporal  | musical/performance progression  |
| Prosodic  | affective modulation             |
| Spatial   | typographic/spatial arrangement  |

---

## Narrative Ontology

`<narrative>` does not represent objective reality.

Narrative content is interpreted as a projection generated by a narrator model.

Narrators MAY be:
- unreliable
- dishonest
- hallucinating
- delusional
- temporally inconsistent
- partially reconstructive

CNML discourse is therefore epistemically unstable by default.

---

## GEL Relationship

CNML MAY contain internally persistent ontologically-oriented metadata and semantic structures.

GEL MAY additionally provide external persistent semantic grounding.

Evaluators MAY:
- privilege internal CNML semantics
- privilege external GEL semantics
- merge both systems
- resolve conflicts heuristically

CNML persistence and GEL persistence are therefore orthogonal but interoperable.

## Narrative Structure Layer

Narrative structure elements organize experiential progression.

```xml

```

### Containment

- `<act>` MAY appear only inside `<mainmatter>`
- `<chapter>` MAY appear only inside `<act>` or `<mainmatter>`
- `<scene>` MAY appear:
  - inside `<chapter>` or `<act>`
  - directly inside `<story>`

All are optional.

### Frame Headers

Zero or one of each of the following:

- `<title>`
- `<synopsis>`
- `<subheasing>`

MAY appear once inside:
- `<series>`
- `<story>`
- `<book>`
- `<section>`
- `<act>`
- `<chapter>`
- `<scene>`

|----------|--------------------------------|
| irrealis | generated experiential content |
| memory   | retrieved experiential content |

##### Volition

| Value       | Meaning                  |
|-------------|--------------------------|

| voluntary   | deliberate invocation    |

##### Mapping

| Element   | Source   | Volition    |
|-----------|----------|-------------|
| dream     | irrealis | involuntary |
| fantasy   | irrealis | voluntary   |
| flashback | memory   | involuntary |
| remember  | memory   | voluntary   |

NarrativeMode = (EpistemicSource × Volition)

## Prosody

Prosody is a compositional modulation system.

### Dimensions

```xml
<quiet>     <loud>
<calm>      <excited>
<gentle>    <forceful>
<smooth>    <harsh>
<engaged>   <detached>
<emph>      <deemph>
<nonverbal>
```

#### Semantics

Prosody:
- modifies expression quality
- does not alter discourse structure
- composes recursively
- is evaluator-interpreted

---

### Integrity Operators

```xml
<redacted>
<censored>
<corrupted>
```

#### Semantics
These indicate intentional or unintentional corruption of representation.

examples:

`<redacted extent="severe" source="narrator" mode="blacked">The text of this span has been mostly redacted by its creator.</redacted>`
`<censored extent="moderate" source="government" mode="blanked">The text of this span has been partially censored by the government.</censored>`
`<corrupted extent="mild" source="eldritch" mode="zalgo">This text has been slightly corrupted by eldritch forces, and appears as zalgo text.</corrupted>`

## CiNnaMoN (Cognitive-Narrative Musical Notation DSL)

CiNnaMoN is a structured, human-readable temporal annotation layer for expressive or performative text segments.

Music elements may appear as semantic content inside ANY CNML container.

### Core Element

```xml
<music time="" beat="" key="" mode="" tempo="" mood="">
```

#### Attributes

* `time`: the number of beats in a measure (numerator of time signature). May be a positive integer or positive real (1, 2, 3, 4, 5, 6.5, 3.1415926535, pi, √2, etc.).
* `beat`: the note-value unit representing the beat (inverse duration of the beat). Defines the denominator of the time signature (e.g. 2 = half note, 4 = quarter note, 5 = fifth note, 8 = eighth note, 16 = sixteenth note).
* `key`: tonal center (A–G with optional accidentals, e.g. `C` for the key of C natural, `Gsharp` for G sharp, `Aflat` for A flat)
* `mode`: modal context (major, minor, lydian, phrygian, dorian, etc.)
* `tempo`: may be descriptive (adagio, moderato, allegretto) or numeric (real number) in beats per minute (120)
* `mood`: descriptive or desired emotional outcome

### Inheritance Rules (Measure Scope)

Within a given measure (bar):

* The first explicit note MUST define:

  * pitch
  * octave
  * duration

* Subsequent notes within the same measure MAY omit any of these fields.

  * Missing pitch, octave, or duration values inherit from the most recent explicitly defined values in that measure scope.

* Inheritance resets at each new measure boundary (`|`).

### #CiNnaMoN Grammar

The content model is line-oriented and token-based.

#### Top-level structure

```
<music> ::= "<music" attributes ">" content "</music>"

attributes ::= (time | beat | key | mode | tempo | mood)*
```

#### Content model

```
content ::= bar ("|" bar)*

bar ::= sequence

sequence ::= element (whitespace element)*
```

#### Element types

```
element ::= note | rest | tie | caesura | text
```

#### Note syntax

```
note ::= pitch ":" duration "{" lyric "}" 
       | pitch ":" duration
       | pitch "{" lyric "}"
       | pitch

pitch ::= [A-G] accidental? octave?
accidental ::= "#" | "b"
octave ::= [0-9]
```

##### Duration

```
duration ::= [0-9]+ "/" [0-9]+   // e.g. 1/4, 3/16
```

##### Rest

```
rest ::= "R" (":" duration)?
```

##### Tie / sustain

```
tie ::= "~"
```

* Ties connect preceding and following notes or sustain state across elements.

##### Caesura / breath mark

```
caesura ::= "//"
```

* `//` is a **caesura or breath mark**, not a comment.
* CNML does NOT define comments in CiNnaMoN.
* No comment syntax exists.

##### Spoken Language
###### Composer-Interpreted Rhythm (Pitchless Beats)

Spoken language MAY be encoded as pitchless timed beats with attached vocal content.

Example:

```
X:3/8{Here} X:1/8{is} {two} {mea-} {sures} {of} X:1/4{spo-} {ken} {vo=} {cals}
```

Semantics:
- `X` = pitchless articulated beat
- rhythm is explicitly composed
- performer timing follows written structure
- lexical segmentation is aligned to beat events

---

###### Performer-Interpreted Rhythm (Rest-Based Vocals)

Spoken language MAY be encoded as rests with attached vocal content, where timing is performer-determined.

Example:

```
R:1/1{Here is one measure of spoken vocals}
```

Semantics:
- `R` = rest event carrying vocal payload
- temporal placement is interpretive
- rhythm is not explicitly fixed beyond measure span
- performer determines pacing and segmentation

---

### Semantics

* CiNnaMoN is non-binding and does not enforce timing
* It represents structured performance intuition over text
* Lyrics in `{}` bind phonetic/semantic alignment to musical events
* Missing octave/duration is resolved via intra-measure inheritance rules
* Ties (~) indicate sustained or blended musical state
* Bars (`|`) segment temporal grouping and reset inheritance scope
* Caesura (`//`) introduces a breath, pause, or interruption in performance flow

### Composition Rules

* Music elements may be nested inside any CNML container
* Multiple `<music>` tags may exist per discourse unit
* Music does not override discourse or prosody semantics

## PÂTE (Poetry Algebraic Typography Engine DSL)

### Overview

PÂTE is a spatial projection layer for CNML.

It defines typographic and geometric relationships between textual spans using deterministic constraint-based layout.

PÂTE is independent from CNML core structural frames.

---

### Core Model

PÂTE operates on:

- spans
- anchors
- geometric relations
- affine offset expressions

Layout resolves through iterative fixed-point evaluation until convergence.

---

### Span Syntax

```text
{{#span_id :: content}}
```

Example:

```text
{{#line1 :: Here is some text}}
```

---
#### Anchors

Anchors may be defined inside span text.

```text
{{#anchorName}}
```

Example:

```text
{{#line1 :: Here is an {{#pivot}}anchor.}}
```

Anchors:

- are geometric reference points
- do not render independently
- are immutable after layout construction

#### Spans

A span is the fundamental layout unit.

Spans contain:

- textual content
- geometric extent
- implicit anchors

All spans possess:

| Anchor | Meaning       |
|--------|---------------|
| left   | leading edge  |
| center | midpoint      |
| right  | trailing edge |

---

#### References

Anchors are referenced using:

```text
@span.anchor
```

Examples:

```text
@line1.center
@line1.pivot
```

#### Width References

Span widths are first-class geometric values used in offset arithmetic.
Access of span width is via `.width`:

```text
2/3 * span1.width
```

#### Measure Spans

Measure spans participate in layout/geometry calculation but are omitted from rendering.

Syntax:

```text
{{#id:measure::content}}
```

Example:

```text
{{#tripleM:measure::MMM}}
```

The span width evaluates from rendered content geometry exactly as with normal spans.

Measure spans may therefore act as reusable geometric constants.

---

### Alignment Syntax

General form:

```text
{{#id; alignment-expression :: content}}
```

Example:

```text
{{#span2; @span1.center |> tripleM :: text with its leading edge displaced from the centerline of span1 by the geometric width of tripleM}}
```

---

#### Alignment Operators

| Operator | Meaning                                          |
|----------|--------------------------------------------------|
| `<`      | trailing edge aligned to anchor line             |
| `>`      | leading edge aligned to anchor line              |
| `|`      | center aligned to anchor line                    |
| `<| d`   | center aligned, offset left by displacement `d`  |
| `|> d`   | center aligned, offset right by displacement `d` |

---

#### Alignment Semantics

##### Edge Pinning

###### `<`

The span hangs to the left of the anchor line.

Its trailing edge touches the anchor line.

###### `>`

The span hangs to the right of the anchor line.

Its leading edge touches the anchor line.

---

##### Center Alignment

###### `|`

The span center lies on the anchor line.

---

##### Offset Center Alignment

###### `<| d`

The span center is displaced left from the anchor line by `d`.

###### `|> d`

The span center is displaced right from the anchor line by `d`.

---

##### Arithmetic Expressions

Offsets support affine arithmetic over rational values and span widths.

Allowed operations:

- addition
- subtraction
- multiplication by rational constants

Examples:

```text
2 * measureSpan
1/2 * title - 3/4 * subtitle
```

---

### Constraint Model

PÂTE constraints are affine-linear.

Layout variables are resolved using deterministic iterative fixed-point evaluation.

Constraint graphs may contain cyclic dependencies.

---

#### SCC Evaluation

Constraint graphs are decomposed into strongly connected components (SCCs).

- acyclic SCCs resolve topologically
- cyclic affine SCCs resolve iteratively until convergence

Evaluation order within an iteration is order-free and snapshot-isolated.

---

#### Geometry

PÂTE geometry is renderer-derived.

Widths and anchor positions are determined by the underlying text layout engine.

Examples include:

- TeX engines
- PDF layout engines
- browser typography engines
- PostScript renderers

PÂTE itself does not define glyph metrics.

---

#### Convergence

Layout evaluation terminates when positional delta falls below epsilon.

Recommended epsilon:

```text
10 µm
```

This epsilon is a convergence threshold only and is not a coordinate unit system.

---

### Rendering

PÂTE MAY be rendered into:

- SVG
- HTML/CSS
- PDF
- canvas systems
- other typographic projection systems

Rendered appearance depends on the target layout engine.

---

#### Determinism

Given identical:

- source text
- fonts
- renderer behavior
- layout configuration

PÂTE evaluation produces identical geometry.
